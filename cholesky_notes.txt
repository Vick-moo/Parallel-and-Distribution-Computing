Cholesky Decomposition - 代码逻辑笔记
================================================================


一、程序整体在做什么
----------------------------------------------------------------

1. 生成矩阵
   - 用 xorshift64* 随机数生成器，固定 seed = 12345
   - 先填下三角随机数 [-1, 1)，再镜像到上三角，保证 A[i][j] = A[j][i]
   - 对角线 = 该行其他元素绝对值之和 + 1
   - 这样构造出来的矩阵一定是正定（SPD），Cholesky 不会失败

2. 分解
   - 标准 Cholesky-Banachiewicz 算法：A = L * L^T
   - 三重循环：
       for i = 0..n-1
         for j = 0..i
           sum = L[i][0..j-1] 和 L[j][0..j-1] 的点积
           如果 i == j: L[i][i] = sqrt(A[i][i] - sum)
           否则:       L[i][j] = (A[i][j] - sum) / L[j][j]

3. 计时
   - 用 steady_clock（单调时钟，不会因为系统对时往回调）
   - 只把分解循环包在计时区里，矩阵生成和 L 清零都不计时
   - 每个 size 重复 reps 次，记录最快一次和平均

4. 输出
   - 5 个 size：1000 / 1500 / 2000 / 2500 / 3000
   - 打印表格：baseline 和相对倍数、best time、average time


二、正确性验证逻辑（重点）
----------------------------------------------------------------

目的：证明算出来的 L 真的满足 A = L * L^T

步骤：
  1. 拿程序算出的 L
  2. 重新计算 L * L^T
  3. 和原来的 A 逐元素比较，记录最大差值
  4. 差值接近 0 就是对的，差得多就是错的

代码：
  double max_abs = 0.0;
  for (int i = 0; i < n; i++) {
      for (int j = 0; j <= i; j++) {        // L 是下三角，只看 i >= j
          double s = 0.0;
          for (int k = 0; k <= j; k++) {
              s += L[i][k] * L[j][k];       // 这就是 (L * L^T)[i][j]
          }
          double e = fabs(s - A[i][j]);     // 和原矩阵对应位置比
          if (e > max_abs) max_abs = e;     // 记录最大误差
      }
  }
  printf("verify max|A-LLt| = %.3e\n", max_abs);

为什么只算 i >= j：
  - L 是下三角，上三角全是 0
  - A 是对称的，A[i][j] = A[j][i]
  - 所以只检查下三角就够了

判断标准：
  - 1e-12 ~ 1e-10：正常，浮点舍入误差
  - 1e-3 以上：算法写错了

为什么要验证：
  - 代码写错时程序不会报错，只会输出一个错的 L
  - baseline 是 parallel 版本的参考答案，参考答案本身必须先核对
  - 验证只跑一次，不计入 benchmark，不影响性能数据
  - 报告里可以写 "max |A - LL^T| = ..." 作为证据

为什么 parallel 版本不能要求 bit-exact：
  - 浮点加法不满足结合律：(a+b)+c 和 a+(b+c) 末位可能不同
  - 并行归约的加法顺序和单线程不同
  - 验证要用 relative tolerance，比如 1e-9，而不是 ==


三、为什么并行版的瓶颈是内存（第 5 点逻辑）
----------------------------------------------------------------

1. 算法工作量
   Cholesky 大约要做 n^3 / 6 次乘加。
   n = 3000 时约 45 亿次。

2. 数据在哪
   A 和 L 各 3000 * 3000 * 8 字节 = 72 MB，两个共 144 MB。
   普通 CPU 的 L3 cache 只有 8-32 MB，装不下。

3. CPU 怎么拿数据
   寄存器 -> L1 -> L2 -> L3 -> 内存，越往后越慢。
   数据不在 cache 里就要去内存拿，CPU 只能等着。

4. 结果
   实测只有 1.15 GFLOP/s，而 CPU 单核峰值是几十 GFLOP/s。
   说明大部分时间在等内存，不是在算。这就是 memory bound。

5. 为什么多线程救不了
   内存带宽是共享的。4 个线程一起去内存拿数据，
   带宽不会变成 4 倍，很快就饱和。
   就像 4 个人共用一个水龙头，接水速度不会变 4 倍。

6. 为什么不能直接 parallel for 外层 i
   Cholesky 有依赖：算第 i 行要用前面已经算好的第 j 行（j < i）。
   如果多个线程同时算不同的 i，线程算 i=3 时 i=1 可能还没算完，
   读到的就是没算完的数据，结果直接错（data race）。

7. 正确的并行方式
   - 按列：第 j 列算完后，i > j 的 L[i][j] 互相不依赖，可以并行
   - 波前（wavefront）：沿对角线斜着一波一波算
   - 分块（blocked）：把矩阵切成小块，一块一块处理

8. blocked 为什么能加速
   把大矩阵切成能放进 cache 的小块（比如 256x256），
   一次只处理一块，这块数据留在 cache 里反复用，
   不用每次都去内存拿，内存访问次数大幅减少。
   块和块之间还可以并行，任务粒度也更适合多线程。

六、CUDA 版本
----------------------------------------------------------------

文件：
  cholesky_cuda/cholesky_cuda.cu
  cholesky_cuda/build.bat

编译：
  先运行 vcvars64.bat 初始化 MSVC，再执行
  nvcc -O3 -std=c++17 -arch=sm_89 -o cholesky_cuda.exe cholesky_cuda.cu

算法：column-oriented right-looking
  for j = 0..n-1:
    1. L[j][j] = sqrt(A[j][j])            1 个线程
    2. L[i][j] = A[i][j] / L[j][j]        n-j 个线程
    3. A[i][k] -= L[i][j] * L[k][j]       (n-j)^2 个线程，2D grid

  update kernel 里 threadIdx.x 对应列 k，保证写 A[i][k] 时 coalesced。

实测（reps=5，RTX 4050 Laptop，sm_89）：

  n      CPU ms     GPU best ms    speedup
  1000   133.319    28.364         4.70x
  1500   447.450    62.983         7.10x
  2000  1208.472   169.673         7.12x
  2500  2802.033   496.965         5.64x
  3000  4828.948   731.322         6.60x

  全部 PASS，误差 2.501e-12 ~ 1.046e-11。

注意：
  - GPU 用 right-looking，浮点求和顺序和 CPU left-looking 不同，
    误差比 CPU 略大，但仍远低于 1e-9 的阈值。
  - RTX 4050 的 FP64 吞吐只有 FP32 的 1/64 左右，是加速比的限制因素。
  - 没有做 tiled 优化（Phase 3 已取消）。
